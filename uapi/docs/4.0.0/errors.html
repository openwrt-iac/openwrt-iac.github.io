Errors

The error model is RFC 7807-inspired but not strictly conformant. application/json throughout. Success responses are the resource value at top level (GET/POST/PUT 2xx body is the resource; no { "data": {...} } wrapper). DELETE success is 204 No Content with X-Request-Id and no body, except on system/cron_jobs, where it is 200 with the entry that it removed. Errors always carry the envelope below.

Envelope

Every non-2xx response carries this body shape (Content-Type: application/json):

{
  "code": "validation_failed",
  "message": "Field 'ipaddr' is not a valid IPv4 address",
  "request_id": "01HX1234567890ABCDEFGHJKMN",
  "errors": [
    { "field": "ipaddr",  "code": "invalid_format", "message": "must be a valid IPv4 address" },
    { "field": "netmask", "code": "required",       "message": "is required" }
  ]
}
  • code is machine-readable, snake_case, stable within a package major.
  • message is human-readable English. Don't parse it.
  • request_id is a ULID echoed in the X-Request-Id response header on every response, success or error. Pair with the audit log line to trace a request server-side. Clients may supply their own via X-Request-Id header or ?request_id= query param, each validated against ^[A-Za-z0-9_-]{8,128}$. The header wins when it matches. When neither form matches, the server generates a ULID.
  • errors[] is only present for 422 validation_failed. All field errors are reported together so the client can fix everything in one round trip.

Top-level codes

HTTP code When
400 bad_request Malformed JSON, wrong shape, body where none expected, a query parameter value that the endpoint does not declare (a limit outside 1 to 500, a family other than v4 or v6 on dhcp/leases, a managed other than true or false on a curated list, a validate other than 1 on /uapi/diagnostics), an Idempotency-Key on a POST that does not match ^[A-Za-z0-9_-][A-Za-z0-9_.:-]{0,127}$, no body on a PUT/PATCH, a key or string with a NUL or a control character other than tab, newline and carriage return, which uci cannot store, or the body of a POST, PUT or PATCH that has not arrived in full 10 s after the start of the request, which is checked before the bearer check
400 invalid_cursor Empty or malformed ?cursor=, one referencing no current item, or one that ends on an unmanaged section when an item up to that section changed
401 unauthorized No Authorization header, or one that is not Bearer <token>
401 invalid_token Token not in store, expired, or source IP not in allowed_cidrs (either address family)
403 insufficient_scope Token valid, scopes don't cover this verb/path
403 scope_escalation_blocked POST /uapi/tokens requested scopes outside the caller's
403 tls_required Non-localhost client over plain HTTP
404 not_found Resource does not exist
405 method_not_allowed Verb not supported on this resource
409 conflict Duplicate name, dangling cross-reference, etc. Also a write whose package another writer, such as LuCI or a shell, changed during the request so that the writes of the request no longer apply. Nothing was written, and a retry reads the new state
409 unmanaged_resource Tried to write to a section that needs to be adopted first
409 idempotency_key_conflict Same Idempotency-Key reused with a different body
412 precondition_failed Stale If-Match ETag, a matching If-None-Match on a write, or JSON Patch test op mismatch
413 payload_too_large A POST, PUT or PATCH whose body is over 262144 bytes (256 KiB), sent with a Content-Length or chunked, whose Content-Length is not a whole number from 0 to 262144, or whose body holds more than 2000 { and [ characters. All are checked before the bearer check and before the JSON parse. On every path, uapi reads and drops what is left of a body before it answers, up to 10 s after the start of the request
422 validation_failed Body parsed but failed schema or per-field rules
423 locked Another write transaction holds a lock on the same package (or the global lock for a non-uci writer); retry. The response message names the specific lock.
429 too_many_requests Per-token rate limit exceeded
500 internal_error Bug or unexpected condition
500 reload_failed_restored Daemon reload failed, or a daemon that uapi watches stopped after it. uapi rolled back the uci change
500 reload_failed_unrecovered Reload AND restore failed, the reload of the restore had not ended when uapi stopped waiting for it, or the restore left a package that another writer, such as LuCI or a shell, committed to after the commit of the request, which restore_error names. Loudest case; manual recovery
500 recover_failed POST /uapi/services/{name}/recover: an instance that procd had given up on is still down after the stop and the start, or uapi did not start the service. service and stopped name the service and each such instance
503 service_unavailable ubus unreachable
503 init_script_missing /etc/init.d/<svc> not present for a resource's reload list
503 config_missing /etc/config/<package> not present, so a write has nothing to write into: wireless on a router without a radio. A DELETE there answers 404 not_found, because no section can exist. A POST /uapi/batch answers 503 for a DELETE there too, because it commits as one write

unsupported_media_type was reserved and never emitted: uapi never rejects a body on Content-Type (the header only switches a PATCH into RFC 6902 mode). It left the published ErrorEnvelope.code enum in v4 (#323), announced in 3.5.0. Clients branching on it must drop that branch.

batch_partial_failure is special: it appears only in the body of a POST /uapi/batch abort response, with the HTTP status taken from the failing sub-request. The body carries {code: "batch_partial_failure", aborted_at_index, error: <sub-envelope>, reverted: true}.

The reload-failure-restored response carries the init script's exit summary as an extension field:

{
  "code": "reload_failed_restored",
  "message": "Service reload failed; prior configuration has been restored",
  "request_id": "01HX...",
  "reload_error": "network exited with code 1: netifd: interface 'wan' has invalid proto"
}

A daemon that uapi watches and that stops after the reload reads, for example, unbound stopped after the reload, with exit code 1.

The unrecovered case adds restore_error as well. A restore whose reload had not ended when uapi stopped waiting reads reload during restore did not finish: firewall reload was still running when the 20 s that uapi waits for the reloads of a request ran out, so its result is unknown. A restore that leaves a package because another writer committed to it reads another writer committed to the package firewall after the commit of the request, so the restore left it as that writer left it. A restore after which procd still does not start dnsmasq reads reload during restore failed: procd does not start dnsmasq again after the reload of the restore: a stop and a start of dnsmasq did not bring it back.

A recover_failed names the service and each instance that is still down, by its name in service list, as the 200 names the ones that it brought back:

{
  "code": "recover_failed",
  "message": "procd does not run dnsmasq/cfg01411c: a stop and a start of dnsmasq did not bring it back",
  "request_id": "01HX...",
  "service": "dnsmasq",
  "stopped": ["cfg01411c"]
}

The message says why. Besides the case above, it reads only 9.0 s of the reload budget of the request were left, and a stop and a start of dnsmasq can take 10 s when reload_budget_s is below 10, its stop was still running after 3 s, so uapi did not start it, which names every instance of the service, or the start of dnsmasq that followed its stop was still running after 5 s, so whether dnsmasq runs is unknown.

Field-level codes

In errors[].code (only inside 422 validation_failed):

code Meaning
required Required field missing
invalid_type Wrong JSON type (string vs. number etc.)
invalid_format Failed format validator (CIDR, MAC, IP, etc.)
out_of_range Numeric or length bound exceeded
not_in_enum Value not in the allowed set
conflict References a missing or incompatible resource, two fields naming one option disagree, or the field does not apply given another field, for example hostname on a static interface
read_only Field is computed/runtime and can't be set. In /raw/, a .type or id that differs from the section
unknown_field No such field on this resource. id, managed and runtime are tolerated at the top level so a read-modify-write cycle can send the response back unchanged

Two more appear only inside invalid_sections in GET /uapi/diagnostics?validate=1, never in a request rejection, because they describe a section the sweep could not judge rather than a field the caller got wrong:

code Meaning
unreadable The section could not be read into the resource's view at all
sweep_failed The sweep itself threw for that resource; nothing was checked

sweep_failed carries an empty field, and its section reports id: null and managed: null. It is reported rather than swallowed because an empty result for a resource that was never actually checked is the one answer that endpoint must not give.

Field paths

Dotted notation with bracket indexing: match.src_zone, dns[0], rules[2].target.

Response headers

Every response carries:

Header When Notes
X-Request-Id always ULID for log correlation.
Content-Type: application/json always (except 204 no-content / /uapi/metrics text) -
Strict-Transport-Security 200 and error responses (see below) 1 year, includeSubDomains.
X-Content-Type-Options 200 and error responses (see below) nosniff.
Referrer-Policy 200 and error responses (see below) no-referrer (request_id appears in URLs).
Cache-Control 200 and error responses (see below) no-store (token-scoped data).
ETag curated GET 200/304 and write success Quoted hash of this resource's own body (runtime block excluded). Sibling sections do not influence the value. Absent on raw passthrough, the non-uci endpoints and the read-only collections dhcp/leases and network/wireguard_kernel_peers, which therefore support neither conditional GET nor If-Match.
WWW-Authenticate: Bearer every 401 realm="uapi", error="<code>" (RFC 7235 + RFC 6750).
Retry-After: <seconds> 423 locked, 429 too_many_requests Honor with jittered backoff.
Link: <?cursor=...>; rel="next" paginated GETs when more items exist RFC 8288. Keeps the query parameters that the list declares: family on dhcp/leases and managed on a curated list.
X-Next-Cursor: c_<id> paginated GETs when more items exist Convenience companion to Link. A page that ends on an unmanaged section gives c_<id>.<hash>, with a hash of the ETags of the items up to it, because that id is the position of the section in its package.
Idempotent-Replayed: true POST replays via Idempotency-Key Marker that the response was served from cache rather than re-applied.
X-Reload-Status 2xx on curated-resource writes, the POST /uapi/batch 207, and a system/cron_jobs write as unverified only ok = init script reload exited 0 (NOT a runtime-convergence promise). no_reload = no init script ran, because the write changed nothing in uci, or because procd runs none of the daemons that read it, which only a dhcp write can meet. unverified = the write keeps its commit, and whether its daemons take the new config is unknown: an init script was still running when uapi stopped waiting for the reloads, 20 s after the first started, or every init script exited 0 but the dnsmasq --test check after a dhcp write did not finish, because it was killed after 10 s or by another SIGKILL. A cron write logs the note to syslog. stopped = the write keeps its commit, but a daemon that it reloaded is down and procd will not start it again on its own: procd gave up on a dnsmasq instance after the reload, and a stop and a start of dnsmasq did not bring it back, or less than 10 s of reload_budget_s were left for them. X-Reload-Stopped names it. unverified wins over stopped: when the start of dnsmasq has not ended within its 5 s, or another check did not finish, the value is unverified, and X-Reload-Stopped comes beside it. The recovery is POST /uapi/services/dnsmasq/recover, which stops and starts dnsmasq once more. service dnsmasq restart on the router, or a write that changes the dhcp config, starts it too. See docs/operations.md § "Success" means exit 0, not runtime convergence, and § Starting again a service that procd gave up on.
X-Reload-Services curated-resource writes and the POST /uapi/batch 207, when status=ok, unverified or stopped Comma-separated list of init scripts that ran (e.g. firewall, dnsmasq), in order. With unverified, one of them can still be running, and those after it run when it ends, unless it fails. On a batch, the services of the packages that the batch changed, sorted. A daemon that reads the config but that the router can lack, or that the operator stopped, is reloaded and listed only while procd runs it. With all of them running, dhcp/servers and dhcp/hosts answer dnsmasq,odhcpd,unbound, dhcp/odhcpd answers odhcpd,dnsmasq,unbound, dhcp/dnsmasq answers dnsmasq,unbound, system answers system,log,dnsmasq,odhcpd,unbound, system/timeservers answers sysntpd,dnsmasq, and each network resource answers network,odhcpd. Each leaves out a daemon that does not run. A batch that holds a dhcp/odhcpd write lists dnsmasq,odhcpd,unbound.
X-Reload-Stopped curated-resource writes and the POST /uapi/batch 207, when status=stopped, or unverified when the check found an instance down Comma-separated list of the procd instances that stay down, each as <service>/<instance>, such as dnsmasq/cfg01411c. procd will not start them again on its own. GET /uapi/diagnostics lists them under stopped_instances, with the same names, until they run again. POST /uapi/services/<service>/recover starts them again.
X-Kernel-Status 2xx on curated-resource writes, and the POST /uapi/batch 207 Whether the write reached the kernel, not just uci. ok = every interface it targeted was applied. partial = some were applied, and others were skipped or blocked. omitted = the apply set a peer without the endpoint that uci holds for it, as the proto handler does: the handler leaves out the endpoint of a host that does not resolve, or of a port that it cannot read, and keeps the peer. A read shows the endpoint that the kernel holds in runtime.endpoint. omitted takes the place of ok, and of partial when the write also skipped or blocked an interface: X-Kernel-Applied then names only the interfaces that were applied, so a skipped one is an interface that the write targets and the header does not name. blocked = an enabled peer of a targeted interface holds a value for which wg refuses the config of the whole interface, so the interface does not come up, and the write applied no other interface. X-Kernel-Blocked names each such peer. The write keeps its commit, with no restore. uapi neither waits for the restart of such an interface nor applies the write to it: netifd sets the peers from uci at the next setup, once the peer is fixed, disabled or deleted. A write of network/interfaces that leaves a wireguard interface enabled answers blocked too, because netifd restarts the interface, and no_kernel otherwise. skipped = it targeted interfaces and none was applied. no_kernel = the write had nothing for the kernel, because the resource has no kernel path or the write changed nothing in uci. An interface is skipped when it is down or netifd does not know it, which is not a failure: ifup reads the peers from uci. netifd restarts the interface on each peer change, so the apply first waits, up to 8 s, for that restart to end. A restart that does not end in time fails a write that sets a peer, with a restore (reload_failed_restored, or reload_failed_unrecovered when the restore fails too). A write whose operations on the interface only remove peers, a DELETE or a write that disables them, skips the interface instead and keeps its commit: the next setup reads uci, which no longer holds them, and a restore would give their access back.
X-Kernel-Applied curated-resource writes and the POST /uapi/batch 207, when at least one interface was applied Comma-separated interfaces whose kernel state the write changed (e.g. wg0).
X-Kernel-Blocked curated-resource writes and the POST /uapi/batch 207, when a stored peer keeps an interface of the write down Comma-separated peers, each as <interface>/<id>, where id is the one that GET /network/wireguard_peers/{id} takes, an unmanaged section included, such as wg0/cfg0a3b7c. Each is an enabled peer that holds a value for which wg refuses the config of the whole interface. A write refuses each such value that it sends, so another writer, such as LuCI, stored it, or the interface that a link-local %zone names went away. Present with X-Kernel-Status: blocked, and beside partial or omitted when the write also applied another interface. GET /uapi/diagnostics?validate=1 lists each such peer with code conflict on the field "".
X-Kernel-Unread GET /network/wireguard_kernel_peers and a read of one of its entries, when an up wireguard interface could not be read Comma-separated up interfaces with proto=wireguard whose kernel peers uapi could not read, because wg show <interface> dump failed or printed a shape that uapi does not read. The list holds no entry for them. Absent when every up interface was read.
X-Mgmt-Path-Warning 200/204 on a network/interfaces, network/devices or network/bridge_vlans write that moved the caller's own path interface=<id> changed=<fields>, e.g. interface=wan changed=proto,ipaddrs. Advisory: the write already happened and was not refused. On network/interfaces, present only when the written interface is the one this request arrived through and the write moved disabled, proto, ipaddrs or netmask (or deleted the section, reported as changed=removed). network/devices and network/bridge_vlans are matched by device instead, and report device=<name> changed=created or changed=removed when a create or delete names the caller's device or a bridge that device is a port of. Absent otherwise. If the write genuinely severs the path this response never arrives, so GET /uapi/diagnostics reports the same interface ahead of a write. See docs/operations.md "Management-path warning".

uapi uses the X-Reload-* and X-Kernel-* prefixes, and X-Mgmt-Path-Warning, for advisory headers only. Each such header reports what the request did or found after uapi completed it. None of them changes what the status code means, or what a client must send or retry, so a client can pass on each of them as it is, as uapi-mcp gives each one to its agent. docs/versioning.md makes a new such header, or a new value of one, an additive change.

The six transaction-header rows above (X-Reload-Status, X-Reload-Services, X-Reload-Stopped, X-Kernel-Status, X-Kernel-Applied, X-Kernel-Blocked) say "curated-resource writes" rather than "writes" because that is measured, not assumed: raw passthrough (/raw/...) and the non-uci writes (/packages/..., /uapi/tokens, /system/password, /system/authorized_keys, /system/cron_jobs) never reach attach_reload_headers. They return none of these headers, with one exception: a /system/cron_jobs write answers X-Reload-Status: unverified when its reload of cron had not ended at the 20 s bound. Otherwise it reports the outcome in its body as runtime.crond_running, because the init script exits 0 even when crond stops. Until 2.5.0 the OpenAPI document declared the reload pair on those responses anyway, which is why the wording here matters: a client generated from the spec was told to expect a header that was never going to arrive. POST /uapi/batch is not a curated-resource write, but since 3.0.0 its 207 carries the same headers, from the one result of its transaction, which it hands to attach_reload_headers: a batch commits and reloads once for the whole set, so there is one outcome to report rather than one per sub-request. A pure-read batch runs no transaction and carries none of them.

Each entry of the batch results array also has a headers object, with the headers of the response of its own sub-request. It always holds X-Request-Id, as <request_id>.<index>. On a 200 it also holds Content-Type, the four security headers below and the ETag of the body, and on a GET of a collection that has more than 100 items, Link and X-Next-Cursor. It never holds the six transaction headers, because a sub-request runs no commit and no reload of its own. It never holds X-Mgmt-Path-Warning either: a sub-request has no remote_addr, so the guard finds no management path, and a batch cannot warn that it moved the caller's own path.

The four security headers (Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy, Cache-Control) come from the shared envelope builder, so they ride every response whose body it builds and are absent from the ones assembled by hand: 204 No Content, the POST /uapi/batch 207, /healthz, /uapi/metrics and /openapi.json. A 304 Not Modified carries X-Request-Id, ETag and the Cache-Control of the response it replaces, and nothing else.

Every writable resource outside dhcp declares a reload service that it always runs, so X-Reload-Status: no_reload and X-Kernel-Status: no_kernel on a WireGuard peer mean that the write changed nothing in uci, and uapi then ran no init script and nothing in the kernel. A dhcp write reloads dnsmasq, odhcpd and unbound only while procd runs them, so it also answers no_reload when none of them runs. A PUT or a PATCH writes only the options that it changes, and no default that the read fills in for an option that uci does not hold, so a PATCH that names no field, or a PUT or a PATCH that sends what uci already holds, commits nothing. So does the adopt of an anonymous section that another writer named while the request waited for its lock. Such a PUT or PATCH still answers 409 conflict when another writer deleted the section during the request. A PUT of the read still writes what it stores in another form than uci holds, such as a list that uci holds as an option, and the PUT of the read after it commits nothing. A POST or DELETE always writes. A POST /uapi/batch reloads the services of the packages that its writes changed, and none when they changed nothing. In 3.1.0 such a PATCH reloaded the daemon anyway and answered ok, and on a WireGuard peer without an endpoint the kernel apply removed the peer and set it again, which reset its session. In 3.2.0 such a PUT still did.

Retry-After

423 locked includes Retry-After: 1; 429 too_many_requests carries the rate-limit bucket refill estimate. Wait that many seconds (or use jittered backoff) and try again. The 423 lock window is the duration of one atomic transaction (validate, stage, snapshot, commit, reload, possibly restore) and is typically well under a second.
