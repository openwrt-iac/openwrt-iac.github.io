uapi architecture

Reader-facing technical overview. The design contract lives in CLAUDE.md; this document explains the current shape of the implementation: where state lives, how a request is served, what locks are held when, how ETags are computed, how rate limits and metrics are stored, what the failure modes are.

Process model

uapi is not a daemon. There is no uapi process. There is no uapid, no procd service definition, no procmon entry.

The code runs inside uhttpd's existing fork-per-request CGI workers via uhttpd-mod-ucode. A single list ucode_prefix '/api/v3=/usr/share/uapi/main.uc' entry in /etc/config/uhttpd is the entire wiring.

Specifically, uapi shares the default main uhttpd instance with LuCI. Both serve configuration use cases; sharing keeps the footprint minimal and lets uapi inherit whatever TLS configuration the operator already set up for LuCI (acme certs, custom listen addresses, etc.). A dedicated uapi uhttpd instance was considered and rejected: it doubles the runtime cost without earning the isolation back (an attacker who can reach LuCI can already reach the same box).

                         uhttpd parent (always running)
                         ├── compiles main.uc once at startup
                         ├── module-level state warm in parent VM
                         │   (RESOURCES, SINGLETONS, RESOURCE_SOURCES,
                         │    BARE_RESOURCES, BARE_SINGLETONS, VERSION,
                         │    LOGGING)
                         │
        client ─HTTP─►  forks a child per request
                         │
                         child
                         ├── inherits parent VM via copy-on-write
                         ├── handle_request(env) runs
                         ├── any mutation is private to this fork
                         └── exit(0)

Validated in tests/integration/01_concurrency_model_test.sh: 5 concurrent requests against a sleeping endpoint observe at least 2 distinct PIDs (the assertion's floor; uhttpd caps concurrent CGI children at 3), total wall time ≈ 1-2s instead of ≈ 5s.

What this buys us

  • Zero footprint when idle. No process to drive memory cost.
  • Inherits uhttpd's TLS, listener layout, max-connection budget, and the operator's whitelist/blacklist config for free.
  • No supervisor (no procd entry to maintain).

What it costs

  • No in-memory state across requests. Counters, caches, in-flight maps - none of it survives. The metrics and rate-limit subsystems are file-backed for exactly this reason.
  • No timers. commit-confirmed-style auto-revert needs a background tick; the model precludes it. Deferred with prejudice (see docs/roadmap.md).
  • Per-request VM startup cost. uhttpd-mod-ucode amortizes this via the parent's CoW, but the child still calls module top-level once (the copy-on-write avoids reparsing, not re-instantiation).

Lock layout

Two flock files, used in three patterns:

/var/lock/uapi.lock                   shared by uci transactions,
                                       exclusive by non-uci writes
                                       (apk, system/access, cron_jobs)
/var/lock/uapi.pkg.<package>.lock     exclusive per-package; serializes
                                       writes to the same uci package only
Operation Global lock Per-package lock
Read (any) none none
Token last-used stamp (rides on an authed request, throttled to 60s) SH EX on uapi
uci write (any one pkg) SH EX on that one pkg
uci write that restarts unbound (unbound_srv, unbound_ext) SH EX on that pkg and on unbound
uci write (multi pkg, /batch) SH EX on each, sorted lexicographic order
Non-uci write (apk, system/access, cron_jobs) EX none

The interactions:

  • Two writes against different packages: both take SH on the global file (compatible), each takes EX on its own per-package file → run in parallel.
  • Two writes against the same package: both take SH on the global, contend on the per-package EX → the second's LOCK_NB attempt fails, so it returns 423 locked with Retry-After: 1.
  • Two writes that restart unbound, such as one to unbound_srv and one to unbound_ext, contend on the EX of unbound the same way. Otherwise the restart of one would read as a stop to the stay-up check of the other, and a line that unbound refuses in one would fail the other too.
  • A non-uci write (apk install / authorized_keys write) takes EX on the global → refused with 423 locked while any uci transaction is in flight (any package), and refuses new ones the same way until it is done. Apk's own DB lock is downstream; the global EX ensures uapi never has two apk writers in flight.

All locks are non-blocking (LOCK_NB); contention surfaces as 423 locked so the client can decide whether to back off and retry. The HTTP worker never waits for a uapi lock, but libuci's own flocks on a package file block while LuCI or a shell holds them. It can sleep while it holds a uapi lock: the stay-up watch of an unbound reload polls for up to 2 s under the transaction's locks. The restore after a failed reload also waits, for up to 5 s, for libuci's flock on the package file. A load holds that flock while it parses the file, and a uci commit while it reads the file again, writes its temp file and syncs it.

Audit and verification: docs/lock-state-audit.md covers every site in src/ and cli/ that takes an fd, a pipe, a lock, a ubus connection or a uci cursor, with proof of release on every in-request exit path including die(). It also says what runs while each lock is held and what a killed request leaves behind. make lint-lock-audit fails when a site is missing from it.

Transaction recipe

Every write request follows this sequence. Failure at any step short-circuits without uci state change.

  1. Pre-flight checks. For each entry in the resource's reload list, confirm /etc/init.d/<svc> exists and the name matches ^[A-Za-z0-9_-]+$. Miss → 503 init_script_missing with the missing path; no uci write attempted. A service in the resource's reload_if_running list, a daemon that reads the package but that an image can lack or that the operator stopped, such as odhcpd for the dhcp writes, joins the reload when its init script exists and service list names it, which procd does from its start to its stop. That is when the procd trigger of a LuCI save reloads it. Otherwise it is skipped, so it never answers 503, and a reload does not start a daemon that the operator stopped. Then confirm /etc/config/<package> exists, because the uci cursor stores nothing in a missing file and reports that only through a null return. Miss → 503 config_missing with the path. A DELETE checks the file first and answers 404 not_found for a missing one, because no section can exist there, and a client reads a 404 on DELETE as already gone. A POST /batch answers the 503 for a DELETE too, because it commits as one write.
  2. Acquire flock. SH on global + EX on the per-package file (non-blocking). EWOULDBLOCK → 423 locked + Retry-After: 1.
  3. Snapshot. uci_unload(<package>), then uci_export(<package>) captures the package file into an in-memory string. The unload matters: the preview before the lock loaded the package into the cursor, which serves every later read from that copy, so a commit by LuCI or a shell in between was invisible to the write.
  4. Validate. Resource's check_schema_types + validate(json, conn, id, delta, partial) run inside the lock, and validate_new(json, conn) where a resource has one, which refuses only the errors that the write adds (docs/adding-a-resource.md). Any field error → 422 validation_failed with the full set of field errors (not fail-fast); no uci change.
  5. Stage. uci_set / uci_create_section / uci_delete mutate the cursor's copy of the package, and bus.uc keeps the writes in order. Nothing is staged outside the request process (see below). A PATCH skips a set of the value that uci already holds and a delete of an option that it does not hold, so a PATCH that changes nothing has nothing to commit, and it collects no kernel operations. The response body is fromUci of the section read back from that copy. So a write answers the body, apart from runtime, and the ETag that a GET then answers, unless another writer commits to the package while the request runs. runtime is read before the reload, and the commit replays the writes over such a commit, which the body does not show.
  6. Commit. When the request wrote to the package, uci_commit(<package>) loads the package file again, replays the writes over it and writes it through libuci, so a commit by LuCI or a shell while the request ran is kept. A replay that no longer applies → 409 conflict, and nothing is written. A commit that libuci refuses, as on a full overlay, → 500 internal_error. Either way the cursor drops its copy of the package, so nothing later in the request reads the writes that the file does not hold. A request that wrote nothing commits nothing, and skips steps 6 and 7: X-Reload-Status: no_reload, X-Kernel-Status: no_kernel.
  7. Reload. /etc/init.d/<svc> reload per reload_services, via fs.popen, exit code checked. Done directly (NOT through ubus) because ubus-mediated reload is fire-and-forget on OpenWrt; only wait4 on a real child gives back the actual exit bit. procd starts the daemon with its new config on its own, so the init script exits 0 before the daemon has read that config, and a daemon that refuses it stops later. For the reloads that STAY_UP in src/lib/transaction.uc lists, which are unbound and unbound-uci-ext, the write then watches the procd instances of the daemon that ran before it. It polls service list every 100 ms for 2 s, and an instance that procd reports as not running counts as a failed reload. An instance that service list does not show is being restarted, and does not count. The restore runs the same check. A reload of dnsmasq is judged by its config instead, because the reload_service() of dnsmasq.init sends SIGHUP right after procd restarts an instance, and on a slow machine that signal can stop the new process for 5 s with a config that dnsmasq takes. The init script writes the config of each instance before it returns. For each instance that service list shows before or after the reload, the write runs its command with --test, and a refusal counts as a failed reload. That includes an instance that is not running, which procd starts on that config, so a config that dnsmasq refused before the write fails the restore too, as reload_failed_unrecovered. --test parses the config and the files that it includes, and exits. A config that dnsmasq parses but cannot start with, such as two ports that conflict, a lease file in a missing directory or a port that another daemon holds, still answers 2xx. The restore runs the same check. No write waits for the daemon to start, and each pays one parse of the whole config per instance, which grows with its size, and again on a restore.
  8. Kernel apply. For each peer operation the write collected (see below), skip it unless network.interface.<name> reports up, then run the matching wg set. Runs only after the reload returned zero, and reports the same way, so a failure here follows the recipe below. The interfaces actually applied are recorded and reported on the response as X-Kernel-Status and X-Kernel-Applied (docs/errors.md § Response headers), because a skip leaves the peer in uci alone and a caller otherwise cannot tell that from a write that reached the kernel.
  9. On reload, stay-up check or apply non-zero: uci_import(<package>, snapshot) → reload, then reconcile each touched interface against the restored uci. Then 500 reload_failed_restored with the captured stderr/exit summary. If the restore itself fails, 500 reload_failed_unrecovered. uci_import writes the snapshot to .<package>.uapi-restore beside the file that the package names, the target of a symlink included, reads it back, because ucode reports no error from close(), and renames it over that file. A kill or a full overlay leaves the package whole, and a restore that cannot write or rename the file answers reload_failed_unrecovered with a restore_error that names the file. Before it writes, the restore takes libuci's flock on the package file, which waits for a load or a commit in progress, and gives up after 5 s. That orders nothing after it: libuci releases the flock before its own rename, so a LuCI commit that held the lock, or waited on it with the old file open, can rename its file over the restored one, as one libuci commit can over another. ucode has no fsync, so the rename holds against a kill but not against a power cut on a filesystem that writes data back later than the rename, such as ubifs.
  10. On success: 200 with the refreshed resource.

Changes that another writer staged

A read reports what the package file holds, and a write commits only its own changes. A shell stages with uci set in /tmp/.uci, and LuCI stages in a directory per session, /var/run/rpcd/uci-<session>. libuci overlays onto a package that it loads by name the delta file of that name in each directory of its search path, and /tmp/.uci is always in that path: ucode's cursor() adds a delta directory but cannot remove that one. rpcd clears the list itself, which ucode cannot. So bus.uc loads each package by its path, which reads the file alone. A uapi write then neither commits nor deletes what a shell staged, and a later uci commit in the shell replays it over what uapi committed.

This also differs from libuci in one place. A load by name reads /var/run/uci/<package>, libuci's override directory, in place of /etc/config/<package> when that file exists, and a commit by name writes there. uapi reads, writes and restores /etc/config/<package> only. Among the package files of the OpenWrt feeds, only procd's reload_config reads /var/run/uci, and nothing writes it. A package that does not load by its path fails the call rather than fall back to a load by name: a read answers null and a write fails. That includes a name that libuci does not load by name, one that starts with a dot or holds a slash, so the temp files of libuci and of the restore are no packages.

libuci commits a package loaded by path by writing the copy that the cursor holds, without reading the file again. The commit of step 5 therefore reloads the file and replays the request's writes, which keeps a commit by another writer that landed while the request ran, as libuci's own replay of a delta does. A replay that no longer applies, because another writer deleted a section that the request wrote into, fails the commit, and the request answers 409 conflict with a message that names the package. A package that the request did not write is not committed, as libuci skips a commit with no changes, so its comments stay, and it gets no reload and no restore. uci_revert and uci_unload drop the copy and the writes, which is the whole of what the request staged.

Why step 7 exists, and why it shells out to wg

A reload converges a daemon only when the daemon notices its config changed. netifd reads WireGuard peers with config_foreach wireguard_<iface> inside the proto setup step, so editing a peer leaves the parent interface section untouched and /etc/init.d/network reload does nothing at all: the peer was committed to uci and never reached the kernel, and deleting one did not revoke it. wireguard.sh is the only proto handler under /lib/netifd/proto/ that reads its own uci sections, so this affects exactly one resource.

This is a platform-wide defect, not a uapi one. LuCI has it too, and says so in its peer form: "Enable / Disable peer. Restart wireguard interface to apply changes." Its Save and Apply resolves through ubus call uci apply → /sbin/reload_config → a config.change event carrying {"package": "network"} → /etc/init.d/network reload → ubus call network reload, which is the same call uapi makes. That chain is package-granular: it cannot express "interface wg3's peers changed", so a package-wide reload is the only action available to it. uapi knows which resource was written and therefore which interface is affected, so it can do better, and does.

Why not ask netifd to re-apply. Measured on hardware: ubus call network.interface.<i> renew returns in 0 ms, so a failed apply is undetectable, and on failure proto_wireguard_setup calls proto_setup_failed, which takes the interface down. One peer with an unresolvable endpoint_host dropped a working tunnel and its healthy peers while the API answered 200. A down+up restart behaves identically and additionally interrupts a healthy tunnel on every peer edit. Every netifd-mediated path applies the whole interface config as one unit, so one bad peer takes the innocent ones with it.

wg set is the only per-peer path: it is atomic, so a bad endpoint fails that one command and changes nothing, it reports a real exit code, and it leaves the rest of the tunnel running. WireGuard exposes no ubus service for peers (wireguard offers only status/genkey/genpsk/pubkey), which is why netifd itself shells out to wg syncconf and LuCI's own backend shells out to wg. Running wg is therefore not a way around the platform's abstraction for peers, it is the platform's abstraction for peers. uci remains the only config writer, the kernel state is derived from committed uci rather than from the request, and nothing new runs in the background.

src/lib/wg.uc makes every value safe for the shell itself, on the value as uci stores it, because the restore after a failed write reads the peers straight from uci, where a value never passed validate(). Every wg and ip command is an argument list, and run() quotes each argument with shellquote, so no caller can forget one. wg.uc also checks the values before it runs a command: route_prefix keeps an address or a CIDR and drops anything else, and the interface and table names must match ^[A-Za-z0-9_-]+$. The checks alone were not enough: a prefix such as ::/0;id>x; passed route_prefix, because the IPv6 prefix length was read with int(), and ip route took it unquoted. A preshared key is passed as a 0600 file on tmpfs, never as an argument, so it never appears in ps.

route_allowed_ips asks for a route per allowed IP, which netifd installs from the proto handler, so the apply installs them too: without that the peer is in the kernel with no path to it and the flag only half works. They are spelled to match netifd exactly (proto static, scope link on v4) and go into ip4table / ip6table when the interface sets one, since netifd puts them there rather than in main. A route is the prefix as netifd installs it: the length read in base 0, as netifd and ip read it, and the address masked to that length. Routes are compared in that one spelling, so a respelled prefix, or the spelling that the kernel prints, is the same route. A prefix is only withdrawn when no remaining peer and no config route section still wants it, because two peers can carry overlapping allowed_ips. The kernel is never scanned for strays on the request path, only on the reconcile that follows a rollback, so a route uapi did not install is not at risk.

One consequence to know: netifd reports the routes it installs in network.interface.<name> status, and routes installed here are not in that list until the next ifup. The kernel is correct; netifd's bookkeeping lags.

A resource opts in with a kernel_ops(kind, opts, sec_type, existing) hook returning the operations to apply. It reads the uci options rather than the resource view because the view masks preshared_key, and the parent interface off the section type because it is not stored as an option, so a DELETE can only learn it from the section it is about to remove. A rotated public key emits a remove for the old key before the set, or the kernel would keep the previous peer and its access. A disabled peer is removed, matching what netifd omits when it builds the config. A remove takes every key that wg can read from the stored public_key, not only the key on its first line. The kernel holds one peer per key, so a remove then sets again each other enabled section of the interface that holds one of these keys, in uci order, as ifup does.

An interface that is down, or that netifd does not know, is skipped: there is no kernel state to sync and ifup reads the peers from uci anyway. That is also what keeps a peer orphaned by deleting its parent interface deletable.

Multi-package transactions (/batch)

POST /batch composes N sub-requests under one combined snapshot/restore:

  1. Pre-resolve every sub-request's target (path → package + reload services), and check its scope, before the pre-flight checks: their 503 would tell a token whether a package that it has no scope for is installed. An operation out of scope aborts the batch with its 403 before anything runs.
  2. Only WRITE sub-requests contribute to the lock/reload set. Pure-read batches skip lock+snapshot+commit+reload entirely.
  3. Acquire global SH + per-package EX in sorted package order (deadlock-free).
  4. uci_unload() and uci_export() each package into a snapshot, as in step 2 of the single-package recipe.
  5. Run each sub-request in order via BARE_RESOURCES/BARE_SINGLETONS - handlers that skip their own per-package flock + snapshot + commit + reload (since the outer multi_transaction has those covered).
  6. First sub-request status ≥ 400 → abort: uci_revert() each package, return { code: "batch_partial_failure", aborted_at_index, error: ..., reverted: true } with the failing sub's status.
  7. All sub-requests 2xx → uci_commit() each package, run the union of the reload services of the packages that the batch committed, then the collected kernel operations. A batch that committed nothing runs neither. Same failure recipe as the single-package transaction, and a commit that fails part way counts as a failed reload. Either way only the packages that the batch committed are restored: the snapshot of another one would undo what LuCI or a shell committed to it since, such as the delete that made the replay of the batch fail. Each other package is reverted before that, so that the cursor holds no write that uci did not store, and a reconcile reads network from the file. A commit that fails stops there, with no reload and no reconcile: both come after every commit, so neither ran, and the restore puts a package that the batch committed before the failure back before uapi reloads it. A replay that no longer applies then answers 409 conflict, and a commit that libuci refuses answers 500 reload_failed_restored. Sub-requests accumulate into one ordered operation list shared through their sub-context, so a batch touching the same peer twice ends on its last state, and the restore reconciles rather than replaying, since a batch can apply several peers before failing on a later one.

Schema layer

Every resource module exports schema_properties. handler.check_schema_types walks it on every write to enforce:

  • type (string / integer / boolean / array / object / null)
  • enum
  • minimum / maximum
  • pattern
  • items (array element schema, with index-bearing field paths like tags[1])
  • properties (nested object recursion)

A merge PATCH schema-checks the WIRE DELTA only (the merged-with-existing post-image inherits fromUci's string-form view of integer-typed fields, so type-checking the merge would falsely 422 on integer-untouched patches). A JSON Patch body synthesises the full post-image, so that is what gets schema-checked. The full merged body still goes through resource.validate() for cross-field logic, next to the fields that the request names (a JSON Patch without its test operations), so a rule can blame only what the request sent. docs/adding-a-resource.md says when to use which.

Unmodeled uci options: PUT replaces, PATCH preserves

A resource module curates a subset of its uci section's options; toUci emits only those. The write path treats options outside that modeled set differently per verb:

  • PUT (replace) normalizes the section to the modeled set. diff_apply iterates the raw existing section and deletes every option not re-emitted by toUci, including ones the resource does not model. PUT means "this body is the whole resource," so uapi owns the section.
  • PATCH (partial update) preserves unmodeled options. diff_apply_patch computes the modeled footprint as toUci(fromUci(existing)) and only deletes within it (a modeled field the patch cleared). Raw uci options outside the footprint (which toUci cannot emit) are never enumerated, so a PATCH that touches one field leaves a hand-set or stock option like firewall icmp_type / unbound dns64_prefix untouched. This matches RFC 7396 merge-patch and avoids the silent data loss a naive delete-everything-absent would cause.

A consequence: the GET-then-PATCH-self round trip is lossless even for options uapi does not model, but GET-then-PUT-self is not (PUT discards them). Tooling that wants to preserve unmodeled state must use PATCH.

Field errors are deduped by (field, code). Schema errors win over validator errors for the same (field, code) tuple. A validate_new() error is dropped only when one of them has its (field, code): each of its rules on a field is its own error, so that one cannot hide another. The 422 body carries the full set; clients fix everything in one round trip.

ETag derivation

ETag = sha256(canonical_json(body_without_runtime)), truncated to 12 hex chars.

body_without_runtime strips the resource's runtime block before hashing. Runtime fields are live ubus/file state (uptime, signal, lease count) that drifts second-to-second on unchanged config; including them would make ETags non-deterministic and trip spurious 412s.

ETag is per-resource: a function of this section's content only. Sibling sections in the same uci package do not influence each other's ETags, so If-Match fires only when the resource the client is updating has actually changed. (Cross-reference invariants like "rule's src_zone must exist" are enforced at resource.validate() time on every write, not via ETag mixing.)

Two GETs of the same unchanged section always return the same ETag.

Multi-resource collection endpoints (GET /firewall/rules without an id) do not currently carry an ETag. If-Match and If-None-Match only fire on resource-level endpoints; collections operate last-write-wins.

Conditional GET

If-None-Match: "<etag>" (or ?if_none_match=) on a GET: when the response ETag matches, return 304 Not Modified with no body and the ETag header echoed. Cheaper for polling clients (Terraform refresh, dashboards).

If-Match writes (precondition_check)

PUT/PATCH/DELETE with If-Match: "<etag>" (or ?if_match=): when the current ETag doesn't match, return 412 precondition_failed BEFORE any uci write. If-Match: * matches any existing resource. Absent header preserves last-write-wins (opt-in concurrency).

uhttpd's CGI env strips If-Match, If-None-Match, X-Request-Id, and Idempotency-Key (hard-coded allowlist in uhttpd source). All four have ?if_match= / ?if_none_match= / ?request_id= / ?idempotency_key= query-string fallbacks; a reverse proxy in front of uhttpd that forwards the headers still works via the header path.

Rate limit token bucket

Per-token bucket, file-backed at /var/run/uapi-ratelimit/<token-id>.txt containing a float and an integer: <tokens_remaining> <last_refill_epoch_ms>.

On each authed request:

elapsed_ms = now_ms - last_refill
refilled = min(burst, tokens + elapsed_ms * rate / 1000)
if refilled >= 1: allow, tokens = refilled - 1
else:             deny, retry_after = floor((1 - refilled) * 1000 / rate) + 1
write {tokens, last_refill = now_ms} atomically (tmpfile + rename)

Default rate 100/s, burst 200. Configurable via config ratelimit { option rate '...'; option burst '...' } in /etc/config/uapi. Atomic-write (tmpfile + rename) avoids flock contention on the hot path; the worst-case race is one request's worth of drift across concurrent forks, bounded by the burst size.

Worked example: default config, a client sends 250 req/s sustained against one token. Burst absorbs the first 200; the next 50 spaced over 1s exhaust the bucket at 100/s. Steady-state: 100/s through, 150/s rate-limited → 429.

Metrics

File-backed under /var/run/uapi-metrics/. One file per (series, label-set) combination:

/var/run/uapi-metrics/
  uapi_requests_total/
    method=GET/path=%2Ffirewall%2Frules/status=200/token_id=tf_prod.txt   "1247\n"
    method=POST/path=%2Ffirewall%2Frules/status=422/token_id=tf_prod.txt  "13\n"
  uapi_request_duration_seconds_bucket/
    le=0.01/method=GET/path=%2Ffirewall%2Frules.txt
    ...
  uapi_rate_limit_drops_total/
    token_id=ci_bot.txt

Path segments (/ in label values) are percent-encoded as %2F to keep filenames safe; decoded back when emitting. Increments are read-modify-write with atomic rename; concurrent forks may lose increments under heavy contention - acceptable for operational metrics, not for billing.

A token mint and a token revoke, over HTTP and with uapi-token, run token_store.reap_state after their commit and under the lock of the uapi package: the bucket and the last-used sentinel of each token that no longer authenticates are unlinked, and each of its uapi_requests_total and uapi_rate_limit_drops_total files is added to the file with the same other labels and token_id=-retired, then unlinked once the add is on disk. A token that revokes itself records its revoke after the fold, and a request of a token in flight at its revoke can write its bucket, sentinel or series after the reap, so those wait for the next mint or revoke. docs/operations.md § Metrics says what a scrape sees.

A counter is written to a temp file, which is renamed over it only when its size on disk is the size of the line, and a counter file that holds no count is left out of a scrape and starts again at its next increment.

GET /metrics walks the tree, decodes the labels, emits Prometheus 0.0.4 text. Path templates are normalized (/firewall/rules/:id not /firewall/rules/r_01HX...) to keep cardinality bounded as clients create/destroy resources. A path that no route serves is recorded as path="unmatched", and a /raw path keeps its package only when /etc/config holds it (metrics.path_label).

Idempotency cache

POST requests carrying Idempotency-Key (header or ?idempotency_key=) are deduplicated for 24 h:

key = sha256(token_name || "|" || key)
file: /var/run/uapi-idempotency/<key>.json
contents: {
    fingerprint: sha256(token || "|" || key || "|" || body_text),
    status, headers, body
}

On second arrival: - Same fingerprint → replay (Idempotent-Replayed: true marker header). - Different fingerprint → 409 idempotency_key_conflict. - Past TTL → cache miss; the new request runs and re-populates.

Cache hits skip the entire handler stack except auth and the rate limiter - the resource handler never runs. A client retrying a network-blipped POST gets the original response back, never a duplicate resource.

An entry can carry a secret, so it is written 0600 into a private directory, see Where state lives. A store writes its entry under a temp name of its own request process before the rename, so two stores of one key at the same moment each write a whole entry. A package install or upgrade removes the directory, so no entry of an older version stays. At most once an hour, a store removes the entries older than the TTL, so the directory holds the writes of about one TTL. A POST /batch that only reads stores no entry: replaying a read gives nothing that running it again does not give.

Audit and request_id

Every response carries X-Request-Id (a ULID by default; client-supplied via X-Request-Id header or ?request_id= query param, validated against ^[A-Za-z0-9_-]{8,128}$).

One syslog line per successful (2xx) writeable request (POST/PUT/DELETE/PATCH) at NOTICE, plus per-401/403/5xx at WARNING/ERROR. Other 4xx writes get no NOTICE line at all. Reads are NOT audit-logged at NOTICE level (the request_id still appears in any error line). /healthz is excluded from all logging.

Format:

uapi <request_id> <token_name|-> <severity> <code|-> <method> <path> <status> [<duration_ms>ms]

Operator-facing fields use logfmt: bare for identifier-safe values, JSON-escaped otherwise. The request_id correlates a wire response with its audit line, an error report with the line, and (for batches) the batch's request_id with each sub-request's <request_id>.<index> line.

State Location Lifetime
Tokens (salted hash + meta) /etc/config/uapi Indefinite

Routing table names (read) /etc/iproute2/rt_tables Operator-managed, base-files conffile

Rate-limit buckets /var/run/uapi-ratelimit/ Until the first mint or revoke after the token is revoked or expires, else until reboot. One that a request in flight at the revoke writes waits for the next
Idempotency cache /var/run/uapi-idempotency/ 24 h, removed by the next store after that
Metrics counters /var/run/uapi-metrics/ Until reboot. A token's series fold into token_id="-retired" at the first mint or revoke after it is revoked or expires. A token that revokes itself, or that has a request in flight at its revoke, keeps that series until the next
Recent errors /var/run/uapi-error-ring/ The last 20, until reboot
Token last-used sentinel /var/run/uapi-token-update/ Until the first mint or revoke after the token is revoked or expires, else until reboot. One that a request in flight at the revoke writes waits for the next
Apk install lock (apk-internal) Per-operation
uapi global flock /var/lock/uapi.lock Per-transaction
uapi per-package flock /var/lock/uapi.pkg.<pkg>.lock Per-transaction

uapi keeps the rate-limit buckets, the idempotency cache, the metrics counters, the recent errors and the last-used sentinels under /var/run, in directories of mode 0700 with files of mode 0600. It uses one only when state_dir.owned() accepts it: a directory owned by the effective uid of the request process, that neither the group nor others can write. One of its own with another mode is narrowed to 0700. A package install or upgrade, after its uhttpd restart, removes these five directories and the four that an older uapi kept in /tmp, each when it is a directory that root owns. A request of the older version still in flight at the restart can write one of them again.

/var/run is tmpfs on OpenWrt, as /var is /tmp: rate-limit buckets, idempotency entries, metrics counters, recent errors and sentinels reset on reboot. This is acceptable: operational counters that span uptime aren't a uapi responsibility - point a node_exporter or central collector at the box and aggregate there.
